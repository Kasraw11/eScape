eScape Security Plan

Iteration 1 Security Plan

eScape is a sensory-aware navigation app for Melbourne CBD that combines routing, pedestrian counts, and refuge discovery to help users choose calmer walking options. This document describes the current security posture, data flow, storage, and update process for the demo and development environment.

1. Project Overview

The application provides route planning, live crowd context, and nearby refuge discovery. It uses public open-data sources and local services, with a FastAPI backend and a Next.js frontend. The demo is intentionally lightweight and does not require user accounts for the core journey-planning workflow.

The main security goal is to keep the backend, database, and routing services private while exposing only the public web app through a controlled tunnel or deployment layer.

2. Data Handled by the System

  • Journey inputs such as origin, destination, and crowd preference.
  • Pedestrian-count data from City of Melbourne open-data sources.
  • Route geometry and segment-level scoring for walking options.
  • Refuge and point-of-interest data, including category, location, and opening hours where available.
  • Prediction results and alert records generated by the backend.

The current demo is not designed to store payment details or intentionally collect sensitive personal identity data.

3. Where the Data Is Stored

Database

PostgreSQL stores route, sensor, refuge, prediction, and alert data.

Local Runtime

During development, PostgreSQL and OSRM run locally in Docker containers.

Backend

FastAPI reads and writes data through the repository and service layers.

Frontend

Next.js renders the user interface and talks to the backend through the proxy.

The public tunnel or hosted frontend should never expose the database directly.

4. Update Frequency and Process

Data How Often It Changes Update Process
Pedestrian counts About every 15 minutes in production; refreshed at startup in the demo launcher. Backend pulls from the City of Melbourne pedestrian-count API, validates readings, and upserts them into PostgreSQL.
Predictions After each pedestrian refresh and then on a 10-15 minute schedule in production. A backend job recomputes route/sensor predictions from current and historical counts.
Refuges When the import script is run, typically manually or on a scheduled refresh. Open-data sources are filtered, validated, and upserted into the point-of-interest tables.
Route options On every journey submission. FastAPI calculates route options, sensor matches, and sensory summaries for the selected trip.

5. Data Wrangling and Cleaning

  • Coordinates are validated before storage.
  • Duplicate records are updated instead of inserted again when a stable source identifier exists.
  • Negative or malformed counts are rejected.
  • Counts are normalized into low, medium, and high crowd categories.
  • Route segments are matched to nearby sensors before scoring.
  • Opening hours are only stored when they can be parsed reliably.
  • Unconfirmed or incomplete refuge data is left as unavailable rather than guessed.

7. Security Controls

  • The database and routing service stay local during development.
  • Environment variables hold secrets and API keys.
  • The frontend uses a proxy path to reach the backend instead of exposing internal ports.
  • The public demo URL should go through Cloudflare rather than directly exposing the machine.
  • The backend should fail gracefully if a source API is down.
Recommended posture

Public access only for the web app, private access for backend and database.

Keep demo credentials out of source control and review them before sharing a link.

8. Risks and Limitations

  • Open-data feeds may be stale or temporarily unavailable.
  • Route quality depends on the current routing engine and source data.
  • Refuge opening hours are incomplete for some places.
  • Crowd levels are estimates and should be treated as guidance, not certainty.
  • The current demo architecture is suitable for a class project but not yet for production-grade public exposure.

9. Validation Checklist

  • Confirm the database health endpoint is responding.
  • Confirm pedestrian ingestion and refuge import can run from the launcher.
  • Verify route planning still works after a reboot.
  • Check that the Cloudflare tunnel only exposes the intended public surface.
  • Keep the README and environment examples aligned with the running setup.
